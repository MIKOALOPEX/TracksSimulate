# 0.5.10 驱动倍率与性能分析

本轮只实现驱动倍率；性能部分为日志与代码分析，没有修改碰撞采样、求解迭代、日志频率、同步频率或物理步长。未启动游戏，未操作测试存档。

## 已实现：整环驱动倍率

调试棒右键轮子 → 履带 → 动力/惯量 → 驱动倍率。范围 **0–16**，默认 **1**；同环统一保存，旧存档缺少新字段时使用 1。

`目标带速 = 输入 RPM × 2π / 60 × 导轮半径 × 绕行方向 × 驱动倍率`

计算后仍受“动力限速”裁剪。例如原目标为 3 格/秒，倍率 2 后目标为 6；原目标为 7、倍率 2，但限速为 8 时，实际目标仍为 8。动力限速本轮保留原有 0.1–16 格/秒范围，不提高高速碰撞边界。此次旧日志已有原始目标约 16.653、限速后 8 的情况：这种设置只增大倍率不会提速，需一并调整动力限速。

倍率不改变 Create 轴的输入 RPM、不增加驱动力上限、不取消加速度与摩擦限制，也不对无动力自由滚动速度乘倍率。倍率 0 为零目标速度，仍是受动力控制的履带，不等于断开驱动。实际轮子动画跟随带速；未装配时的展示也使用同一限速规则。多导轮的冲突判定保留，统一倍率不能掩盖相互抵触的输入。

物理日志新增 `drive_multiplier`；`target` 是放大后的目标，`limited_target` 是限速后的目标，`speed` 是接触作用后的实际带速。网络参数协议升级，服务端仍验证范围、权限和调试棒。

离线 build、prepareClientRun 和现有检查通过；新增 15 项检查覆盖默认值、正反转、倍率上限、零倍率、非法值、参数往返、限速，以及真实 Belt.motor 计算仍受驱动力限制。它们不是游戏载荷/高速驾驶验收。

## 原因判断：优先排查顺序

现有日志没有分阶段耗时、CPU 调用栈、分配量或 GC 停顿，无法声称某个函数占了 70%，也不能保证某项优化能恢复多少 TPS。以下为日志负载与当前实现共同支持的热点候选。

### 1. 接触数量乘以高频、多层迭代，优先级最高

日志全部显示 `dt=0.005`，即每模拟秒 200 个子步（掉 TPS 后不等于墙钟仍执行 200 次）。`ContactSolver.solveGroups` 每次固定做 24 轮；每个接触中还进行摩擦椭圆求解，滑动时内部最多 24 次，未饱和时可在第一次提前结束。

按十车窗口的约 39.5 接触/环粗略估算：20 环 × 39.5 × 200 × 24 ≈ **379 万次接触外层处理/模拟秒**；内层在最坏情况下可再放大到约 9100 万次。这个数量级估算不是 profiler 实测，不能把所有接触都算成满 24 次摩擦搜索。外层还包含有效质量、悬挂映射、速度和冲量计算及临时向量创建。

### 2. 每个子步重新遍历带段与体素，且动态车体扩大查询组合

`BeltPhysics.prepare` 每子步重新生成约 0.45 格间距的物理段、支撑映射、OBB、候选接触；包含整个带环，不只下部。每段对地形及环范围内的其他车体调用 `gather`，枚举查询包围盒内的格子，对碰撞体调用 `ContactBox.surfaceContact` 的最多 15 轴 SAT。

已有 `Frame.cells` 缓存，同一车辆同一子步内两环可共用，不能说“完全没有缓存”。但每车每子步创建新 Frame，缓存不能跨子步/车辆复用；裸邻格形状查询也不经过这个缓存。动态障碍对每个带段再做坐标变换和格子扫描。当前没有持久接触集合或碰撞结果热启动，密集车群会放大这一成本。

### 3. 临时对象、字符串和日志 I/O 是额外负担

SAT 每次创建轴列表和多个不可变 V3；求解器在高频循环中不断创建向量。是否已被 JIT 消除、剩余分配量与 GC 停顿均需 JFR 确认，不能仅凭源码认定 GC 是主因。

每环 `beltSample` 每子步 `String.format` 一次状态文本：20 环在模拟满速时约 4000 次/秒，而 GUI 与网络不需要这个更新频率。`PhysicsDiagnostics` 默认每 5 个游戏 tick 输出，异常每 2 tick；持续穿透触发高频异常记录。`DiagnosticLog.append` 同步做目录检查、文件大小检查以及 Files.write，实际会反复开关文件。19:34:50–59 约 1.10 MB / 217 条日志：数据带宽并不巨大，但字符串格式化与同步 I/O 可能拉长物理步。不能仅凭日志量认定它是第一瓶颈。

控制器约每两个游戏 tick 同步，负重轮运动超过阈值时也发送包含配置/路径/材质的块实体数据；这是次级候选，需要统计包数量、字节数与序列化耗时。

### 4. 车辆相互接触没有统一的求解状态

当前同车多环共享 Frame，但不同车体分别建 Frame、求解并提交反作用。彼此接触的多车没有作为统一接触组处理，既重复构造障碍和惯量数据，也可能增加响应不一致及深穿透。这里只能指出架构风险，不能从现有日志证明所有动态接触都被重复计算或它就是穿透的唯一原因。

## Gearwork 中值得借鉴的设计

已阅读本机提供的 Gearwork 1.0.0 反编译分析文件，仅参考架构，不复制 ARR 实现。

- `track/physics/TrackPhysicsSubstepSolver.java`：把运行段分为接触区域，采样后汇总力，并按车体限制施力；不是把整圈密集带段的每个体素命中都放进多轮接触求解。
- `TrackContactSampler.java` / `TracksConfig.java`：每个区域使用有限射线，默认 4，可选 1/2/4/9；将命中拟合为等效平面/加权接触区域。
- `compat/sable/SableWorldRaycastBackend.java`：批处理持有 LevelAccelerator、忽略对象集合及世界容器；射线先筛选车体，并在车体局部边界裁剪。这里的 batch 是复用查询上下文，不能把名字理解成已经并行计算。
- `track/attachment/TrackBodyAttachment.java`：连接集群查询带刷新间隔（20 个 sequence），避免每次重新计算相同拓扑。

适合借鉴的是**有限接触区域、查询上下文复用、拓扑缓存和按车体汇总**。直接照搬向下射线会损失本项目的带面侧碰、顶面碰撞、水平安装、异形带环及未来受弹判定，因此不采用这种功能退化方案。

## 后续验收建议

不额外私自运行性能测试。未来实施优化后由用户在同一存档、相同视距/物理设置、倍率固定 1 下测试：1/5/10 车分离平地运行、10 车接近/碰撞、双流原地转向、45°坡、侧翻/水平安装、多条履带、可移动重载和静止休眠。Gearwork 对照应尽量一致，同时注明它与本项目的碰撞能力不同。

短时 JFR 和摘要日志分别看服务器物理耗时、分配/GC、同步及客户端耗时；画面隐藏只能作为区分客户端竞争的对照，不能证明服务器碰撞性能。目标是十车独立运行稳定 20 TPS、总体 p95 不超过 50 ms/tick，履带预算争取不超过 10–15 ms/tick；这是验收目标，不是已实现或有保证的提速结果。

另发现复制车体复用了 loop UUID：同一会话只有两个 UUID，却有多个车体实例。现有物理运行注册按车体区分，不能把它误判成只有两条履带；但 0.5.9 的跨世界失效返还登记仅按 loop UUID，存在拆除一份复制品影响其他复制品的风险。后续需为复制实例生成新环标识或采用实例级登记；这不是当前 TPS 下降的已证实原因，本轮遵照“仅分析”未修改生命周期。
